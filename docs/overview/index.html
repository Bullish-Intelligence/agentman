Overview

What agentman is

agentman is a CLI for talking to typed agents while retaining a durable record of the work. It is designed for exploratory and operational agent use where a conversation is not disposable: model requests, streamed events, outputs, snapshots, and tool effects should remain inspectable after the process that created them exits.

The record is the product. DBOS supplies durable workflow execution and recovery, but agentman does not treat durability as a generic excuse to replay side effects. Tool effects are recorded as evidence and surfaced for inspection; resume is refused when the evidence is not sufficient.

Recording guarantee

For an accepted turn, agentman gives the turn one canonical run identity and records the durable lifecycle across the product run store and the step_persistence journal. Model and tool lifecycle events observed by StepPersistence, snapshots, messages, output, and supported file-effect evidence remain inspectable through the daemon after the client exits. The journal, not the live SSE stream, is the source of truth.

“Recorded” deliberately does not mean:

  • every physical model or tool execution happens exactly once;
  • an SSE client receives every event or a dropped event can be reconstructed from the stream;
  • an unrestricted shell command receives file pre/post evidence;
  • an unknown shell or filesystem effect is automatically replayed after a crash;
  • a client-side Python output type is imported by the daemon; or
  • a final result exists when the workflow fails before it can produce one.

Recovery supplies facts and refusal policy. It does not turn arbitrary external side effects into transactionally safe or generally replayable operations.

The three nouns

NounMeaningIdentity and scope
AgentA YAML pydantic-ai AgentSpec, plus agentman’s output: and tools: extensionsA named spec discovered from global or repository configuration
ThreadA named, resumable conversationA generated id scoped to a resolved workspace
RunOne turn: workspace + thread + agent + model + prompt → outputThe DBOS workflow id; also the pydantic-ai and journal run id

There is intentionally no separate batch, capability, grant, receipt, or workflow-mapping product noun. Fan-out is a client convenience that creates ordinary runs. Capabilities are pydantic-ai/harness implementation details.

What a complete turn does

At a high level:

  1. The CLI resolves the workspace, config, agent spec, output type, model string, and current thread.
  2. The repository interpreter generates the output JSON Schema when the agent is typed.
  3. The client sends a self-contained request over the Unix socket. It sends JSON Schema and agent data, not repository Python imports.
  4. The daemon resolves the model, loads thread history, starts one DBOS workflow, and streams pydantic-ai events back as SSE.
  5. DBOS and harness persistence record the workflow and semantic journal while agentman records the product-facing run row.
  6. The daemon returns the structured JSON result.
  7. The client validates that result in the repository interpreter and prints either the stream/result or canonical JSON.

The history source is the harness snapshot from the thread’s most recent settled run, with the product run’s stored messages_json as a fallback when a snapshot is unavailable.

What agentman deliberately does not claim

  • A recorded tool call is not automatically exactly once.
  • A crashed arbitrary shell command is not safe to replay.
  • SSE is not the authoritative record; it is a live presentation of events.
  • Wall-clock overlap proves agentman adds no serialization; it does not by itself prove that the model server decoded requests in one batch.
  • A model constrained to JSON Schema can still produce semantically wrong values; client-side pydantic validation remains mandatory.
  • Moving or renaming a repository preserves the record but changes the workspace identity used by convenience lookups.

Deliberately absent capabilities

The current design does not include Markdown view files, file watching, a Neovim plugin, a second database, SQLite as a daemon fallback, a shared model alias registry, repo-id hashing, system boundaries, Nix agent composition, automatic replay of unknown effects, or a generic exactly-once tool wrapper. These are not hidden bugs; they are scope decisions. Their review triggers are listed in the roadmap .
